# Asset Manager: Firebase setup

Asset Manager now uses Firebase Authentication (email/password) and Cloud Firestore.
It uses a **separate project**, not E-Voucher's project. HR Hub and E-Voucher are unchanged.
The app is not connected until the web configuration and project setup below are complete.

1. Create/select the separate project in Firebase Console and register a web app.
2. Copy `apiKey`, `authDomain`, `projectId`, and `appId` into `firebase-config.js`.
   Never put a service-account private key in browser files.
3. Enable Authentication > Sign-in method > Email/Password and add the deployed website's
   hostname to Authentication > Settings > Authorized domains.
4. Create a Cloud Firestore database (default database, Standard edition).
5. Publish the contents of `firestore.rules` in the Firestore Rules editor.
   Alternatively, from this directory, use the Firebase CLI after signing in:
   `firebase deploy --only firestore:rules --project YOUR_ASSET_MANAGER_PROJECT_ID`
6. Create each authorized user's email/password account in Firebase Authentication.
   Existing Supabase accounts and passwords are not automatically transferred.
   For each allowed user, create `asset_manager_users/{FIREBASE_AUTH_UID}` in Firestore
   with the boolean field `active: true`. This record must be provisioned by an administrator;
   browser users cannot grant themselves access. Setting it to false revokes register access.
   A local helper interface is available in `admin-user-manager/` to create the Auth user and
   access document together after you add a Firebase service account key.
7. Serve the intranet directory through HTTP(S), not file://, so browser module imports work.
8. Sign in, add a test asset, reload, verify search and CSV export, and sign out.
   Check unauthorized users are denied. Delete the test record using the console when done.

## Data and access

- The login page's signup form creates accounts directly with Firebase Authentication
  and saves the full name on the Auth profile. It does not use the local admin server.
  Email/Password must be enabled in Firebase. Register access still requires an
  administrator-provisioned `asset_manager_users/{uid}` document with `active: true`;
  signing up does not grant administrative or register permissions.

- `assets/{tag}` stores the existing register fields plus `created_by`, `created_at`, and
  `updated_at`. Timestamps are generated by Firestore; the UI sorts on `created_at` descending.
- Asset tags are case-sensitive and use 1-100 letters, digits, underscores or hyphens,
  starting with a letter or digit. The tag is the document ID. Transactional creation prevents
  accidental overwrites and concurrent duplicate tags.
- Only staff with an active access record can read/create assets. Client updates and deletes
  are disabled because the current UI does not implement those operations.
- Existing SQL files and `supabase-config.js` are retained as legacy reference only.
  Neither live HTML page loads the Supabase SDK or configuration anymore.
- Depreciation, maintenance, disposal and settings remain previews, as before this migration.

## Existing Supabase records

No records have been copied or deleted. Keep the old database until the new register is verified.
Export `public.assets` to JSON from Supabase, then import using a trusted Firebase Admin script
or the console. Preserve the register fields, convert timestamps to Firestore Timestamps, use each
validated `tag` as the document ID, and map `created_by` to an authorized Firebase UID.
Resolve duplicate or unsupported tags first. Compare record counts, total purchase cost and total
book value before switching production traffic. Do not import old database credentials into the browser.

Live sign-in, deployed rules, and live read/write verification require the new project configuration
and an authorized account. Those checks have not yet been performed.
